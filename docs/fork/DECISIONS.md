Filing (`fork::filing`, `f0016_filing.sql`). Rules are a local setting, `Folder: description` per line, so the folder list and its wording never enter this public repository. For each Inbox conversation in the last 30 days Jev is asked one question per rule about its newest Inbox message (description as the yes criterion, "a real person or a notice to act on" as the no). At or above 0.7 (setting, never below 0.5) the conversation's Inbox copies move to the folder through the existing `move` op, creating the Gmail label on first use. The highest score wins between two rules.

Never filed, whatever the score, with every Inbox message of the conversation checked, not only the newest: a Deals conversation, a starred one, one the user wrote in, mail from inside the company (own domain and the Colleagues list), a conversation with Inbox mail from more than one sender address (a platform relays real people from its own domain), a message without a Message-ID, the Never-file and Priority Always lists, calendar mail, sign-in and reset notices, unauthenticated mail, and mail that Priority or To reply scored over its own bar (Priority never scores bulk mail, so for most of it Jev's one answer is the only judge). A rule may not name a system folder (Spam, Trash, Archive and the rest are refused by name, and any folder with a role is refused as a destination). Moving a filed message back (the "Jev filed this" bar's Undo, or by hand) puts the sender on a per-rule never list: the log is keyed by account and Message-ID because thread ids do not survive a move, and a logged message back in the Inbox counts as moved back once 10 minutes have passed and no move is pending on the account (a retry poll can bring rows back while the op waits). A move the server refuses for good does not fail toward the Inbox on its own: the local Inbox rows were removed at once and the forward-only sync would return only mail newer than what is held. `recover_failed` lowers the Inbox `last_seen_uid` below the op's lowest UID so the next sync fetches those messages again, closes their log rows without a never-file entry, and drops Filing back to preview with a notice in Settings.

Mode off, preview or on. Preview scores and lists what would move in Settings without moving anything; Patrick sees that list before on. Questions are capped at 2000 a day, 40 a pass, each message and rule asked once; scores kept 120 days.

Thread files (`ThreadFiles.svelte`, `fork_thread_files`). A strip sticky at the top of the reading pane lists every non-inline attachment in the conversation, newest message first, read from the attachment rows rather than loaded bodies; a message whose copy in this folder has no rows borrows them from another folder copy of the same message. Messages flagged with files but not downloaded show a "Files in N more not downloaded yet" link that loads them. One line of pills, each opens the file in its usual app; "All files" opens the existing chips with Save all and a jump to each file's message.

`priority::Ask` criteria became `Cow<'static, str>` so a rule's description can be the yes criterion.

## D73: a draft written elsewhere keeps its links, lists and bold; blank lines survive the plain part (1.1.26)

Patrick: "not rendering rich text in drafts (like hyperlinks)". An agent had created a Gmail draft whose HTML part carried a booking link; its text part held only the link's words. `edit_draft` builds the local draft from the text part alone, so the rich editor opened the words with no link, and a send or an edit from Skim would have sent the HTML part without it (the HTML part is built from the editor's stored words). Gmail web drafts lost their links, lists and bold the same way.

The composer now asks `fork_draft_source` for the server copy's stored body (HTML and text, only while the copy is still in Drafts) and `openingHtml` picks the editor's words:

1. The server copy's words, unless this build has already stored the editor's words for the draft (f0017 adds `fork_draft_html.rev`; rows written from 1.1.26 on are 1 and the server copy is then never offered, so a link the user removed cannot come back from a server copy the write-back has not replaced yet) or an older build stored HTML with formatting of its own. The HTML is cut at its quote or signature (`gmail_quote`, `gmail_signature`, `blockquote[type=cite]`, Skim's own `skim-words` / `skim-sig`, Outlook and Thunderbird markers) and cleaned with the paste allowlist. It is used only when it carries formatting the text cannot and its words match the plain words letter for letter (layout, punctuation, list marks and either rendering of a link's URL ignored). A table or hidden text refuses it: the editor would run the cells together or show a preheader. A draft with no text part opens from its HTML.
2. The stored editor HTML, when it says what the words say, blank lines aside (rows stored before this change were checked against a body without them).
3. The words as plain lines, as before.

The body is rebuilt from the chosen HTML before the loaded shape is taken, so opening a draft is never an edit and never rewrites the server copy; the text part then carries "words (URL)" for each link. A draft opened once by 1.1.25 has a stored row (rev 0) without the link: it has no formatting, so the server copy still wins.

`htmlToText` dropped every blank line (`<div>a</div><div><br></div><div>b</div>` read as "a\nb": the block after an empty block took its place). It now closes a line at each block's start and end and treats a BR as the end of a line, so it is the inverse of `textToHtml`, tested in Chromium with the real Squire build (`compose-html-dom.test.mjs`). `<p>` and headings, which only come from HTML written elsewhere, get the blank line their margin shows, and a spacer paragraph (`<p>&nbsp;</p>`) is that same blank line, so an agent's paragraphs keep their spacing in the text part. With blank lines back, a reply paragraph starting "On" could pass for the quote's attribution, which only had to have " wrote:" somewhere after it: `quoteAt` (composer), `ownWords` (the AI-tell scan and the forgotten-attachment check) and `attribution_line` (Rust) now need "On … wrote:" on one line, the first such line. The scheduled-send list snippet (`scheduler.rs`) still cuts at any paragraph starting "On"; it only shortens a preview.

Validation: 21 deliberate faults in the new logic each failed a named test (four first survived and got a sharper test, or, for a second guard that duplicated the word match, the guard was removed); a read-only pass over the owner's four server drafts with HTML: both with a link open with it, the one with a list keeps it, the two plain ones open as before, and Squire round-trips each with no input event.

Known limit: a Gmail web reply whose text part wraps the attribution line over two lines does not split, so its words do not match and it opens from the text as before.

## D75: one click copies an address; Drafts and Sent catch up within a minute (1.1.28)

Patrick: "can you make one click on email address copy? also, there seems to be latency between mails showing in skim vs gmail online (also, drafts going to sent etc)".

Copy: `fork/reading/CopyAddress.svelte` is the address as a borderless button; a click writes it to the clipboard and toasts "Copied <address>". Used for the sender, every To and Cc line, and the CRM drawer's address fields. A name stays plain text; only the address copies.

Latency: measured at the time of the report, Skim and Gmail agreed (newest inbox message, all four drafts, no stuck mail ops). The gap is structural: IDLE watches INBOX only, and Drafts and Sent waited for the five-minute poll unless that folder was open. A draft sent or deleted in Gmail web, the phone or by an agent therefore stayed a draft in Skim for up to five minutes. Two changes:

1. Every 60 s the engine STATUS-probes Drafts and Sent and syncs only a folder whose snapshot moved (the snapshot `sync_all_folders` already keeps). STATUS is refused on the selected mailbox, so a selected target is first swapped for a read-only EXAMINE of INBOX; CLOSE is never used because it expunges.
2. Window focus also runs the full STATUS-gated sweep (`sync_now`), at most once per 20 s, so returning from Gmail web catches every folder.

Read-state changes made elsewhere still wait for the five-minute poll on folders other than the open one: STATUS UNSEEN catches them only for unread counts that moved.
